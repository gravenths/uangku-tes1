================================================================================
KEPUTUSAN TEKNIS PENTING
================================================================================

1. `deleting` bukan `deleted` di TransaksiObserver
   -------------------------------------------------
   AuditLog memiliki kolom transaksi_id dengan constraint FK nullOnDelete.
   Jika kita menangkap event `deleted` (setelah baris transaksi sudah terhapus),
   FK transaksi_id langsung menjadi null sebelum AuditLog sempat diinsert —
   akibatnya kita kehilangan referensi transaksi mana yang dihapus.
   Dengan menggunakan event `deleting`, transaksi masih ada di database saat
   AuditLog dibuat, sehingga transaksi_id dapat diisi dengan benar.

2. Lock ordering untuk mencegah deadlock
   --------------------------------------
   Saat transaksi pindah akun (akun_lama → akun_baru), kedua baris akun
   harus di-lock. Untuk menghindari deadlock antar sesi konkuren, lock selalu
   dilakukan dengan urutan id terkecil terlebih dahulu (lock by min id first).

3. Kolom data_lama & data_baru disimpan sebagai JSON
   ---------------------------------------------------
   Sesuai PRD rekomendasi 8.2, kedua kolom tersebut bertipe `json` di skema
   database, bukan string/text biasa. Di sisi Model, keduanya di-cast dengan
   $casts = ['data_lama' => 'array', 'data_baru' => 'array'] agar Laravel
   otomatis serialize/deserialize saat baca-tulis.

4. Laporan tahunan per user (bukan global)
   ----------------------------------------
   Tabel laporan_tahunan memiliki kolom user_id dan unique constraint pada
   kombinasi (tahun, user_id). Ini lebih granular dibanding skema lama yang
   menyimpan laporan secara global, dan memungkinkan setiap user memiliki
   laporan tahunan independen.
